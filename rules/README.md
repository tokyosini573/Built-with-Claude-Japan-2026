# ルール（世界エンジンの数値）

世界エンジン（`teppuri/engine/`）が使う数値は、すべてこのフォルダの YAML にあります。
**バックテストの前に固定します。** 値を変えたら `docs/iterations.md` に理由を書きます。

| ファイル | 中身 |
|---|---|
| `presets.yaml` | アプリ種類4つ（matching / subscription / habit / shopping）のリテンション、登録率、核心行動、決済、特別規則。関門（本人確認など）、決済後の継続、価格の扱い |
| `channels.yaml` | 広告チャネル7つ（instagram, x, tiktok, youtube, line, transit, offline）の単価・CTR・届く人、クリック→設置率 |
| `multipliers.yaml` | Claude の判断（higher / similar / lower）の倍率、ペルソナの関心（interest）の倍率、人ごとの揺らぎ、傾向（trait_*）の係数、クチコミ（身近な人づて・X 上の拡散） |
| `sensitivity.md` | 感度表。仮定を1つずつ low / high に振ったときの A/B の決済者と「B が良い確率」（`python -m teppuri.engine.sensitivity` で作り直す） |

## 出典の読み方

各値は次の形です。

```yaml
signup:
  low: 0.466
  mid: 0.466
  high: 0.584
  source: "[LD22] p.18 国別チャート 日本 ITA-Registration 46.61% / [L19] p.9 58.4%"
  note: mid は最新の日本値（[LD22]）。
```

- `source` の `[L19]` などは `data/DATA_SOURCES.md` 3-0 の略称です。その後ろが表・ページ。`3-F` のように章番号だけのものは DATA_SOURCES の該当章の表を指します。
- 範囲の選び方は DATA_SOURCES 3章の規則どおりです: low = 出典の最小値、high = 最大値、mid = 最も新しい日本の値。規則から外れたものは `note` に書きました。
- **`source: assumption`** は出典がない値です。`note` に理由と、置いた値の考え方を書いています。画面と DATA_SOURCES 5章「限界」でも仮定として示します。
- 割合は 0〜1 の小数です（15% → 0.15）。ドル建ての出典は 1ドル = 150円（仮定）で円にしました。

## エンジンでの使われ方

毎日のループ（設計 3-2）。人ごとに 0/1 ではなく確率（期待値）を積み上げます（設計 3-5）。

1. **広告露出**: 1日の表示回数 = 1日の予算 ÷ CPM × 1,000（キャンペーン期間外は0）。表示は「届く人」に、その人が表す実人数（weight）に比例して配ります。
   - オンライン: その SNS を使っている人（人口の `sns_*` 列）× ターゲット（年齢・性別）× 出荷地域
   - transit: 通勤・通学者（employment）× 住んでいる都道府県の鉄道利用率（国勢調査2020）× 出荷地域。年齢・性別では絞れない
   - offline: 学生（employment = student）で 18〜29歳 × 出荷地域
2. **設置**: 1表示あたり設置確率 = CTR × クリック→設置率 × 判断の倍率（install）× 傾向の係数 × ペルソナの関心の倍率（`runs/<app_id>/personas.json` の interest。なければ 1）。1人あたり1日の設置確率 = 1 − exp(−表示回数 × 1表示あたり確率)。まだ設置していない分（確率）にだけ掛けます。min_age 未満とスマホなしは設置しません。出荷地域の外には広告もクチコミも届きません。
3. **登録**: 設置 × 登録率 × 判断（signup）。
4. **関門**: app.yaml の `gates` を順に通ります。審査時間（review_hours）を日数に切り上げ、その日数だけ待ってから通過判定。待ち日数が1日を超えた分は `wait_loss_per_day` ずつ離れます。本人確認は個人情報への不安（trait_privacy）が高い人ほど通りにくい。
5. **核心行動**:
   - matching: 関門を通ってまだマッチしていない人が、毎日 `daily_hazard × 密度係数` でマッチします。密度係数 = n / (n + density_half)、n = 同じ都道府県で関門を通った相手側（既定は異性）のプロフィール累計（実人数）。**近くに相手がいないとマッチが起きない**ので、地域を絞ると率が上がり、全国に薄く撒くと下がります。待っている人もリテンションどおり減ります。
   - subscription / habit: 登録した人のうち `core.rate`。
   - shopping: 初回購入。登録→購入 = 設置→初回購入 ÷ 設置→登録。
6. **継続**: プリセットのリテンション曲線 × 判断（retention）。D1・D7・D30 は出典、D90 以降は D7→D30 のべき乗減衰を延ばした仮定です。エンジンは曲線を指数の和で近似して（出典の点は約3%以内で通る）、人ごとに設置日の履歴を持たずに計算します。
7. **決済**: 価格の扱いは `決済確率 × (価格 / 基準価格)^(−弾力性 × 価格感度の係数)`。
   - matching: 初マッチの日に決済判断。相手が十分いる既存アプリで「設置→有料 5.4%」になるように、初マッチ時点の決済率を逆算します。who_pays（male / female / both）で男女の差（[CFA24]）を付けます。
   - subscription: 無料体験があれば **体験が終わる日** に決済判断（体験→有料）。なければ初視聴の日（ダウンロード→有料）。
   - habit: 無料体験がなければ **設置7日後にまだ使っている人** に決済画面（「7日を越えると残る」）。
   - shopping: 初回購入が決済。その後も使っている人は `repurchase_cycle_days` に1回買います。
   - 決済後は初回更新 62%、その後は12か月で `year1_monthly` になる率で減ります。売上は30日ごとに月額を計上します。
8. **クチコミ**（2つの経路。どちらも (M − N)/M があるので、設置者が市場に近づくほど減り、市場を超えません。誰に起きるかは trait_wom（口コミ依存）と trait_novelty の係数、install の判断倍率に比例します）
   - **身近な人づて（LINE・対面）** `installs_wom_local`: 1日の設置 = q × A × (M − N) / M。A = 前日のアクティブ、M = 出荷地域の市場、N = 地域内の設置済み。地域内だけで起きる。
   - **X 上の拡散（ポスト・リポスト）** `installs_wom_x`: 1日に届く量 = q_x × A_x × (M_x − N_x) / M_x。発信源は使っている人のうち X 利用者（`sns_x`）、受け手は**全国**の X 利用者。出荷地域の外にも届きますが、地域外ではアプリを使えないので設置になりません（届いた分は無駄になる）。`plans.<案>.available_outside_regions: true` のときは regions を広告の出稿地域とみなし、地域外の X 利用者も設置できます。
   - X 経由の認知・設置の割合は調査に見つからなかったので、q_x は仮定で範囲を広め（20倍）にとっています。

### Claude の判断

`runs/<app_id>/decisions.json`（契約 §3）の level を `multipliers.yaml` の倍率にして、上の各段階の確率に掛けます。判断に `person_id` があればその人の判断を揺らぎなしで使います（契約 v2）。その人の判断がある人（その案で1つでも）には、ペルソナの関心（interest）の倍率を掛けません（判断が本人に合うかを既に含むので二重計算になるため）。なければ `cluster_id` の判断を受け継ぎ、`person_jitter_sd` の対数正規の揺らぎが入ります。install は広告素材ごとの判断を平均します（予算を素材で等分）。判断がない段階・クラスターは similar（倍率 1.0）です。

### 傾向の係数

`multipliers.yaml` の traits は、人口全体の加重平均が 1 になるように割り直してから掛けます。平均はベンチマークのまま、人による差だけが生まれます（価格感度だけは弾力性に掛けるので割り直しません）。

## 運営中のアプリから始める・途中の変更（契約 v2、バックテスト用）

app.yaml の plan に任意で書けます。書かなければ結果は従来と完全に同じです。

```yaml
initial_state: {active: 300000, payers: 30000, as_of_day_since_launch: 365,   # 日本全体の実人数
                ever_installed: 5000000,   # 任意: 累計設置者（やめた人を含む）。無ければ推定
                monthly_churn: 0.03}       # 任意: 既存の決済者の月次解約率（公開値があるとき）
changes:
  - {day: 31, pricing: {monthly_jpy: 4900}, applies_to: all}   # all = 既存の決済者にも次の更新日から / new = 新規の決済だけ
  - {day: 31, pricing: {monthly_jpy: 4900}, applies_to: all, phase_in_days: 90}   # 既存の決済者は90日かけて均等に新価格へ
  - {day: 31, pricing: {order_jpy: 5000}}                       # shopping の1回の注文額
  - {day: 31, channels: {instagram: 0}}                         # その日から止める
  - {day: 60, channels: {tiktok: 3000000}, campaign_days: 30}    # 60日目から30日で300万円
```

- **過去に設置した人（ever_installed）**: やめた人を含む累計設置者を、設置できる人（min_age・地域・スマホ）に、プリセットの属性の傾向（matching は `initial_affinity`: 既婚・離別の重み、assumption）× 判断の倍率（install・retention）× ペルソナの関心 に比例した確率で配ります。このうち active の割合が今使っている人です。過去に設置した人は広告・クチコミで設置し直さず、クチコミの (M − N)/M の N に入ります（市場の飽和）。今使っている人はクチコミの発信源とマッチの相手側（プロフィール）になります。
- **ever_installed の推定**（入力に無いとき）: 発売から as_of 日まで一定のペースで設置されてきたとみなし、1日の設置 = active ÷ Σ_{a=0..as_of} R(a)、ever_installed = 1日の設置 × (as_of + 1)。R はプリセットのリテンション曲線（D90 以降はべき乗の延長）。上限は設置できる人の数。例: matching で active 30万人・365日なら約500万人。
- **今使っている人の継続**: 成熟期の曲線 `E(t) = R(as_of + t) / R(as_of)`（発売からの日数の位置から続ける）。新規と同じ初期離脱は当てません。matching で as_of = 365 日なら月に約3%減ります。
- **既存の決済者**: 成熟期の月次解約率で減ります。`initial_state.monthly_churn` があればその値、無ければ `paying_retention.mature_monthly_churn`（2% / 4% / 7.6%、high は出典から計算した1年目の平均、low・mid は assumption）。新規の決済者も13か月目以降はこの率です。更新日は30日に均等に散らばるとします。
- **値上げ**: 新規の決済判断は変更日からの価格で行います。`applies_to: all` のときは既存の決済者にも次の更新日から新しい価格を当て、その更新で `(新価格/旧価格)^(−弾力性)` の割合だけ続けます（値上げのときだけ。値下げで戻ってくる人は入れない）。`phase_in_days` があれば、既存の決済者はその日数をかけて均等に新価格へ移ります。
- **shopping の値上げ**: `pricing.order_jpy` の途中変更で、初回購入の確率に `(新注文額/最初の注文額)^(−弾力性 × 価格感度)`、再購入の頻度に `(新注文額/最初の注文額)^(−弾力性)` を掛けます。
- **予算の変更**: 書いたチャネルの予算をその日から置き換えます。合計を `campaign_days`（書かなければ元のキャンペーンの残り日数、終わっていれば30日）で等分します。
- **daily.paying**: その日に払い続けている人数（既存の決済者を含む）。`totals.paying_end` は最終日の値です。`daily.payers` と `totals.payers` は新しく決済した人だけです。
- **区間の集計**: `teppuri/engine/window.py`。`interval_band(daily_runs, 31, 120, "sum")` は回ごとに区間を集計してから分位点を取ります。リプレイ JSON しかないときは `interval_from_replay(replay, "A", "revenue_jpy", 31, 120)`（日ごとの分位点を集計する近似）。
- 限界: ever_installed を推定するときの「一定のペースで獲得」と、今使っている人の成熟期の曲線は形の仮定です。公開値があれば ever_installed・monthly_churn を入力してください。

## 範囲の抽選（30回）

- 1回ごとに、各値について u（0〜1 の一様乱数）を1つ引き、**中央値が mid になる二分一様分布**で値にします: u < 0.5 なら low〜mid、u ≥ 0.5 なら mid〜high を一様に。
- 同じプリセットのリテンションの点（D1・D7・D30）は同じ u を使います（曲線の形が崩れないように）。
- **A案と B案は同じ回で同じ抽選値・同じ人ごとの揺らぎを共有**します。違いは案の中身からだけ生まれるので、比較が公平になります。
- 30回の結果から p10 / p50 / p90 を出します。
- 31回目として、全ての値を mid にした回を1つ計算し、地図と個人の話（`sample_run.events`）だけに使います。

### sample_run.events の意味

1人は約9,680人を表します。1人を 0/1 で抽選すると、500万円の広告でも1万人の中の設置が1人前後になり、地図に何も出ません。そこで mid 回の確率で「この人が表す約9,680人のうち、何人がその段階に進んだか」を整数で抽選し、1人以上いた日に `[person_id, 日, 段階, 人数]` を出します（契約 v1）。段階は install / signup / gate:<id> / core_action / trial / pay / churn。churn はその人のグループで使うのをやめた人数です。

## 出力の流れ（契約 v1）

```bash
.venv/bin/python -m teppuri.engine.run apps/<app_id>/app.yaml --runs 30      # → runs/<app_id>/engine.json
.venv/bin/python -m teppuri.engine.build_replay <app_id>                   # → web/public/replays/<app_id>.json
```

`build_replay` は engine.json に、あれば `runs/<app_id>/interviews.json`（interviews）と `report.json`（report_ja、themes → drop_themes）を入れます。無ければ空のままです。daily は `active` だけが「その日に使っている人数」、ほかは「その日に新しく起きた数」。累計は `daily_cumulative`（回ごとに累計してから分位点）。`comparison` は同じ回どうしの B − A の差と、B が良かった回の割合です。

## 限界

- ベンチマークの限界は `data/DATA_SOURCES.md` 5章のとおりです。特に: デーティングのリテンションは 2018-19 年の日本データ1本、D90 はどのカテゴリにも出典がない、SNS の CPM・CTR は代理店ブログの相場（3次）とグローバル値、日本単独の 体験→有料 はない（APAC で代用）。
- **仮定の値**（`source: assumption`）: 為替、既存利用者の配分の重み（既婚・離別）と継続の形、ペルソナの関心の倍率、X クチコミの強さ、クリック→設置率の逆算に使う CPC 基準（値自体は出典から逆算）、電車広告・大学の 接触→設置率、マッチの起きやすさと密度、サブスク・習慣の核心行動率、習慣の決済画面の日、関門（本人確認以外）の通過率と審査待ちの離脱、価格弾力性、再購入周期、判断の倍率、人ごとの揺らぎ、傾向の係数、クチコミの強さ。
- クリック→設置率は CPC ÷ CPI の逆算です。計測会社の CPI（$5.5 前後）と代理店相場（100〜250円）で約4倍違うため、範囲が広くなります。
- 交通広告の料金は首都圏の媒体のもので、全国に当てはめています。鉄道利用率は 2020年（コロナ期）で、テレワーク補正はしていません。
- 登録率・購入率は広告経由の設置ベースと推定されるもので（DATA_SOURCES 5章-6）、クチコミ経由の設置にも同じ率を使っています。
- 決済後の継続（RevenueCat）はサブスク全体の値で、デーティング単独ではありません。
- 決済後の継続課金と売上は、人ごとではなく合計で計算しています（判断の retention 倍率は決済後の継続には効きません）。

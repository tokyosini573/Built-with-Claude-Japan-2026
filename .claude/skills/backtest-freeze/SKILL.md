# バックテストの固定順

設計 5章。精度を測るのではなく、方向を当てられるかを見る方法の点検。**順番を飛ばさない。** 各段階は別々のコミットにし、メインセッションがコミットする。

## ① ルールを固定する
- [ ] `rules/*.yaml`、`teppuri/engine/`、判断のプロンプト（`teppuri/judge/prompts/`）、倍率に未コミットの変更がない（`git status`）
- [ ] `pytest` が全部通る
- [ ] コミット: 「バックテスト①: ルール・倍率・プロンプトを固定」。このコミットのハッシュを控える
- これ以降 ③ まで、上のファイルを変えない。変えたら ① からやり直し、`docs/iterations.md` に理由を書く

## ② 入力だけを足す
- [ ] 事例の入力（`apps/` の各事例の app.yaml と、`backtest/` の質問ファイル）。**アプリ名を書かない**。運営中のアプリは `initial_state`、途中の変更は `changes`（契約 v2）
- [ ] 正解・結果を思わせる記述が入力にない
- [ ] `git diff --stat` が入力ファイルだけ
- [ ] コミット: 「バックテスト②: 事例の入力」

## ③ 予測をコミットする
- [ ] 各事例をエンジンで実行し、質問ごとに「はいの確率」（30回中の割合）を `backtest/predictions.json` に書く
- [ ] 比べる単純モデル（「いつも伸びる」「予算が大きいほうが勝つ」）の予測も同じファイルに入れる
- [ ] 予測のあと、Claude に「このアプリが何か分かるか」を別に聞いて記録する（分かった事例は別集計。除外はしない）
- [ ] `git diff --stat` が予測だけ（①のファイルに変更がない）
- [ ] コミット: 「バックテスト③: 予測」。**このコミットより前に `backtest/answers.yaml` は作れない**（PreToolUse の hook が止める）

## ④ 正解を入れる
- [ ] 正解はリポジトリ外の封印フォルダ（非公開）から写す。正解を調べたのは入力を作ったのとは別の担当
- [ ] `backtest/answers.yaml` に出典（URL・資料・ページ）付きで書く
- [ ] コミット: 「バックテスト④: 正解」

## ⑤ レポート
- [ ] 当たり数と Brier 点数を、テプリと単純モデルで並べる
- [ ] 外れた質問も全部 `backtest/report.md` と画面に出す
- [ ] 「約20問は方法の点検で、精度の測定ではない」と書く
- [ ] Claude がアプリを見抜いた事例は別に示す
- [ ] コミット: 「バックテスト⑤: レポート」

## 確かめ方（審査する人向け）
```bash
git log --oneline -- rules/ backtest/predictions.json backtest/answers.yaml
```
①→③→④ の順に並び、③ のあとに `rules/` の変更がないことが見える。

# バックテスト

テプリが「条件を変えたあと、指標が増えるか減るか」という**方向**を当てられるかを、実在の日本のサービスの公開資料で点検します。正確な数字ではなく方向を見ます。17問は方法の点検であって、精度の測定ではありません。外れた質問も全部 `report.md` に載せます。

## ファイル

| パス | 内容 | 作る人 |
|---|---|---|
| `cases/case_XX/app.yaml` | 事例の入力（6事例）。契約 v2 の `initial_state`（変化前の規模）と `changes`（価格・広告費の変化）。アプリ名・社名は書かず、匿名の説明だけ。推定した値にはすべて「推定、根拠: …」のコメント | メイン（入力担当） |
| `questions.yaml` | 17問の機械可読版（指標、区間 A・B、比べる向き、A〜B の間の変化） | メイン（入力担当） |
| `predictions.json` | 予測（各質問の「はい」の確率と、2つの基準の答え） | `run.py predict` |
| `recognition.json` | 記憶チェック（Claude がどのサービスか分かったか） | `run.py recognize` |
| `answers.yaml` | 正解。**予測をコミットしたあとにだけ置く** | メイン（正解は別の担当が調べた） |
| `report.md` | 結果（的中数と Brier スコアを基準と並べる） | `run.py score` |
| `../web/public/backtest.json` | 公開サイトの表示用（形は `web/src/lib/backtest.ts`） | `run.py export` |
| `runs/<app_id>/` | 判断（`decisions.json` など）と API 応答のキャッシュ。リポジトリの `runs/` とは分ける | `run.py judge` / `predict` |

入力の出どころはリポジトリ外の調査メモ（`03_조사/backtest/cases_inputs.md`、正解なし）です。正解は別の担当が調べ、リポジトリ外の別フォルダに封をしてあります。

## コミットの順番（これが証拠）

1. **ルールの固定**: `rules/`（ベンチマーク・倍率）、`teppuri/engine/`、`teppuri/judge/prompts/` をコミットする。以後、事例に合わせて変えない。
2. **入力**: `cases/`、`questions.yaml`、`teppuri/backtest/`、このファイルをコミットする。
3. **予測**: `run.py judge --yes` → `run.py predict` → `run.py recognize --yes` を実行し、`predictions.json` と `recognition.json` をコミットする。
4. **正解**: 封をした正解から `answers.yaml` を作ってコミットする（ここで初めて正解がリポジトリに入る）。
5. **レポート**: `run.py score` で `report.md` を、`run.py export --prediction-commit <③のコミット>` で `web/public/backtest.json` を作ってコミットする（③のあとにも、正解なし `answer: null` の版を export してよい）。

①〜③の間に正解を見ない。③のあとで入力やルールを直したくなったら、直さずに `report.md` と `docs/iterations.md` に「こう直せば当たった（かもしれない）」と書くだけにする。

## 手順

```bash
# 判断の費用見積もり（API は呼ばない）
.venv/bin/python -m teppuri.backtest.run predict --dry-run
# 判断を取る（Haiku 5.5、Batch API）。--sample N でクラスター比例の標本にできる
.venv/bin/python -m teppuri.backtest.run judge --yes
# エンジンを30回まわして予測を書く（判断は backtest/runs/<app_id>/decisions.json を読む）
.venv/bin/python -m teppuri.backtest.run predict
# 記憶チェック（事例ごとに3回）
.venv/bin/python -m teppuri.backtest.run recognize --yes
# 正解を置いたあと
.venv/bin/python -m teppuri.backtest.run score
# 公開サイト用（正解がなければ answer: null）
.venv/bin/python -m teppuri.backtest.run export --prediction-commit <予測のコミットのハッシュ>
```

- `predict --judge none` は判断なし（全員 similar）でエンジンだけをまわす。`--judge mock` は API を呼ばないダミーの判断（動作確認用）。
- `predict` の既定は `--judge real`。判断がまだない事例があると、`--yes` がなければ費用の見積もりだけを出して止まる（予測は書かない）。
- 予測は決定的（固定シード `20261108`）。同じ入力・同じ判断なら同じ `predictions.json` になる。

## 予測の作り方

1. 事例ごとに `app.yaml` の A 案を、エンジン（`teppuri.engine.simulate.simulate_plan`）で30回まわす。1日目の時点で運営中のサービスとして始め（`initial_state`）、期間の途中で価格・広告費を変える（`changes`）。
2. 回ごとの日別系列から、質問の区間 A と区間 B の値を出す（`teppuri.engine.window.interval_runs`。回ごとに区間を集計する）。
   - `revenue_jpy` + `sum`: 四半期の売上
   - `paying` + `last`: 期末の有料会員数・定期購入者数（`daily.paying` = その日に払い続けている人数。`daily.payers` は新規の決済だけなので使わない）
   - `paying` + `delta`: 四半期の純増減（最終日 − 開始の前日）
   - `arpu` + `ratio`: 区間の売上 ÷ 区間の paying の平均（1人あたり月額単価）
3. 回ごとに B と A を比べ（`greater` なら B > A、`less` なら B < A、同じ値は「いいえ」）、30回のうち「はい」になった割合を予測の確率とする。
4. 日付は `questions.yaml` の `cases.<id>.day1` を1日目として日に直してある。`run.py` は `dates` と `days` が一致するかを毎回検査する。シミュレーション開始の前日の期末（例: 6月末）は1日目の値で代用する。

## 判断（Claude）

- 判断担当の `teppuri.judge.decide` をそのまま使う（Haiku 5.5、1人 × 1案 = 1回、Batch API とプロンプトキャッシュ）。判断は「この人がその段階まで来たとき、カテゴリ平均と比べて進みやすいか」だけで、数字はエンジンが作る。
- 判断に見せるのは `app.yaml` の説明・価格（変化前）・案の条件だけ。**途中の変化（changes）は判断に見せない**（値上げの効果はエンジンの価格弾力性で入る）。画面・広告画像はない。
- 既定は**対象者全員**（最低年齢以上でスマホを持つ人、各事例 約8,500〜8,800人）。見積もりは下のとおり安いので、標本にする理由はない。
- `--sample N` を付けると、事例ごとに N 人をクラスター比例で抜き出して判断を取る。標本外の人は、同じクラスターの標本の多数決（同数なら similar）を受け継ぐ（エンジンは person_id の判断を優先し、なければ cluster_id の判断を使う。契約 v2）。**標本にした場合は `predictions.json` の `cases.<id>.sampled` と `report.md` に出る。** デモアプリは常に1万人全員。
- ペルソナ（Opus）は既定では使わない（判断は属性だけを見る）。`backtest/runs/<app_id>/personas.json` を置けば判断とエンジンが使う。

### 費用見積もり（2026-11-06 の dry-run、判断担当の見積もり機能による概算）

| 取り方 | 呼び出し | 推定（Batch 半額、キャッシュあり〜なし） |
|---|---|---|
| 全員（6事例 × 約8,600人 × 1案） | 51,604 回 | 約 $10.2〜$14.2 |
| 標本 1,000人/事例 | 5,980 回 | 約 $1.2〜$1.6 |
| 記憶チェック（6事例 × 3回、同期） | 18 回 | 数セント |

## 比較の基準

どちらも確率ではなく 0 か 1 で答える（Brier スコアは外れ率と同じになる）。

- **常に増える**: 売上・会員数・単価はいつも増える。純減が「大きくなるか」には「いいえ」。
- **素朴**: 区間 A〜B の間に値上げか広告減（`change_between` の `price_up` / `ad_down`）があれば指標は減る、それ以外（広告増・変化なし）は増える。1人あたり単価だけは値上げで増える。設計 5-5 の「予算が大きい方が勝つ」もこの基準に含まれる（広告増 → 増える、広告減 → 減る）。

## 採点

- `answers.yaml` の形式:

  ```yaml
  # 正解（予測のコミット後に置く）。出典は封をした調査メモ
  answers:
    case_01_Q1: yes
    case_01_Q2: no
    # 出典を画面に出すときは辞書でも書ける
    case_01_Q3: {answer: yes, source_ja: "2025年2月期 決算説明資料 p.5", source_url: "https://..."}
    # … 17問すべて。値は yes / no
  ```

- 的中: 確率が 0.5 より大きければ「はい」と答えたとみなす。ちょうど 0.5 は 0.5 点。
- Brier スコア = (確率 − 正解(はい=1, いいえ=0))² の平均。小さいほど良い。
- テプリ・常に増える・素朴の3つを並べて `report.md` に書く。

## 記憶チェック

Claude が事例を知っていると、判断が予測ではなく記憶になりうる（設計 5-6）。予測のあとで、判断のときに見せたのと同じ匿名の説明（`app.yaml` の内容）を見せて「実在のどのサービスか分かるか」を事例ごとに3回聞く（`teppuri.judge.decide` の `recognition_check`、Haiku 5.5）。**1回でも「分かった」と答えた事例**を「分かった」とし、`report.md` で別に集計する（除外はしない）。

なお、判断が効くのは各段階の倍率（higher / similar / lower）だけで、価格・広告費・会員数などの入力はすべてここで人が入れている。記憶が予測に入る道は判断の倍率だけ。

## 入力の決め方（全事例共通の規則）

公開値がない値は、事例ごとに都合よく選ばないよう、次の規則で決めた（各 `app.yaml` にもコメントで書いてある）。

- **広告費が公開されていない事例**（case_02・03・05）: 変化前の四半期売上の10%を、期間中ずっと同じ水準で出す。売上も公開されていなければ「決済者 × 月額 × 3か月」。
- **広告費の配分**: 内訳の公開がなければ instagram 30% / youtube 30% / x 20% / line 20%。入力に媒体の名前があればそれに寄せる（case_05 は X 中心、case_06 は名前の出た4媒体に均等）。エンジンにない「Web 広告」「アドネットワーク」は youtube・line などで代用。
- **使っている人数（active）**: 有料のみのサービスは決済者と同じ。基本無料で公開されていなければ決済者の3倍。
- **運営日数（as_of_day_since_launch）**: 記載がなければ 1,825日（5年）。
- 期末の会員数がシミュレーション開始日より後の日付しか公開されていない場合（case_01 の5月末、case_02 の5月末）は、その値を1日目にも使う。

- エンジンの任意項目 `initial_state.monthly_churn`（成熟期の月次解約率）・`ever_installed`（累計設置者）・`changes[].phase_in_days`（既存の決済者へ新価格を日数をかけて適用）は、**cases_inputs に公開値がある場合だけ**使い、無ければ書かずにエンジンの既定に任せる。使ったのは case_02 の `ever_installed`（累計利用者 1,730万人）と case_03 の `phase_in_days`（2022年11月〜2023年5月の移行）だけ。月次解約率の公開値はどの事例にもない。

## 経緯: 規則固定の前の試運転

入力（`cases/`・`questions.yaml`）を書いたあと、ルールを固定する前に、**判断なし（全員 similar）でエンジンだけを一度まわした**。正解は見ていない（正解はリポジトリ外に封をしたままで、この時点で開いた人はいない）。試運転の結果から次の4つの**エンジンの構造上の欠陥**が見つかり、エンジン担当が直した。

1. **成熟期の解約**: 運営中のサービスの既存の決済者が、新規の決済者の1年目の継続率で減っていた。長く払い続けている人の多い成熟したサービスでも毎月大きく減り、広告をよほど増やさない限りどの事例も「減る」と答える形になっていた。→ 成熟期の月次解約率（`mature_monthly_churn`、事例に公開値があれば `initial_state.monthly_churn`）で減るようにした。
2. **市場の飽和**: 過去に設置してやめた人が「まだ設置していない人」として扱われ、クチコミと広告の市場が大きく見積もられていた。→ 累計設置者（`ever_installed`、無ければ推定）を入れ、設置し直さないようにした。
3. **shopping の値上げ**: shopping の1回の注文額（`pricing.order_jpy`）の途中変更をエンジンが読んでおらず、case_01 の値上げが予測に効いていなかった。→ 読むようにした。
4. **段階的な移行**: 既存の決済者の一部だけが少しずつ新価格へ移る変化を表せず、case_03 は「ある日に全員」で近似するしかなかった。→ `phase_in_days` を足した。

この直しは「欠陥があった」から行ったもので、試運転の数字が当たりそうか外れそうかを基準にしてはいない（正解を知らないので判断できない）。直したあとの入力の変更は、新しい項目に公開値を入れたことだけ（case_02 の累計設置者、case_03 の移行期間。case_03 はこれに伴い「2023-03-01 に全員を一度に移す」という推定の近似をやめた）。ほかの推定値は変えていない。

## 限界（エンジンで表せないもの）

- **移行の速さ**: case_03 の既存会員の移行は、2022年11月から2023年5月まで均等に移るとした（実際は1月までが遅く、その後が速い）。
- **複数の価格**: Web とアプリ内課金（case_05）、3つのプラン（case_04）、月額と年額（case_02）は1つの価格で代表させた。
- **季節性**（case_04 の「春が需要期」）、ポイント配布、新商品、最低購入金額、送料、海賊版・競合・インフレ、アプリ内広告の収益は入れていない。
- コイン課金（case_06）は月額の継続課金として近似した。
